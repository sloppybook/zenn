## はじめに

私は普段、10年以上運用されている大規模なSaaSの開発に携わっています。
長く運用されているサービスでは、モデルに何十ものコールバックが登録されていることがあります。さらに、複数のConcernがincludeされ、それらのConcernの中でもコールバックが登録されています。

モデルファイルを読んだだけでは、保存や更新のときにどの処理が呼ばれるのか、その処理によってどんな副作用が起きるのかを把握するのが難しい状態です。コールバックを追加した本人には分かっていても、時間が経ったあとに別の開発者が変更すると、影響範囲を調べるだけで時間がかかります。

私自身も、コールバックの存在や実行順序を十分に把握しないまま変更し、不具合を出したことがあります。最近はAIを使ってコードを調査する方法も優秀ですが、調査結果は入力や推論に左右される非決定的なものでもあり、どこまで任せられるかは慎重に判断する必要があります。

特に、コールバックが数多く登録されているモデルは、コア機能を担っていることが多くあります。そのような箇所では、AIによる調査を補助として活用しつつ、最終的には人が登録内容と副作用を確認することが重要だと考えています。

そこで、AIによる調査を補助しつつ、人が登録内容と副作用を確認しやすくするためのGemを作りました。今回が初めてのGem開発です。

作ったのは、ActiveRecordモデルに登録されているコールバックを調べて、モデルファイルにコメントとして書き込む **annotate_callbacks** です。

https://github.com/sloppybook/annotate_callbacks

この記事では、何をするGemなのかと、実装で工夫したところを紹介します。

## モデルのコールバックを一覧で見たい

ActiveRecordのコールバックはモデルファイルを見るだけでは登録されている処理を把握しきれないことがあります。

たとえば、モデルへ直接書いたコールバックと、Concernや親クラスから登録されたコールバックがある場合です。

```ruby
class User < ApplicationRecord
  include Trackable

  before_validation :normalize_email
  after_create :send_welcome_email

  # ...
end
```

このコードだけを見ても、`Trackable`や`ApplicationRecord`で何が登録されているのかまではわかりません。

そこで、**実際に登録されているコールバックを集めて、モデルの近くに一覧として残せたら便利そう**だと考えました。

## annotate_callbacksでできること

Rakeタスクを実行すると、モデルファイルのクラス定義より前に、次のようなコメントを追加します。

以下は出力イメージです。

```ruby
# == Callbacks ==
#
#   before_validation  :normalize_email
#   before_save        :track_changes       if: :changed?  [Trackable]
#   after_create       :send_welcome_email
#
# == End Callbacks ==

class User < ApplicationRecord
  include Trackable

  before_validation :normalize_email
  after_create :send_welcome_email

  # ...
end
```

主な機能は次のとおりです。

- モデルに登録されたコールバックを一覧にする
- Concernや親クラスから継承したコールバックも対象にする
- コールバックメソッドの定義元が別のクラスやモジュールなら、その名前を表示する
- ブロックやlambdaのコールバックは、ファイル名と行番号を表示する
- `if: :active?`など、Symbolで指定された条件を表示する
- Rails内部のコールバックを、名前や定義元などのルールで除外する

コールバックの挙動を変えるのではなく、登録情報を読み取ってコメントにするためのGemです。

## 使い方

開発用途を想定して、Gemfileの`development`グループに追加します。

```ruby
group :development do
  gem "annotate_callbacks"
end
```

```bash
bundle install
```

### 注釈を追加・更新する

Railsアプリケーションのルートで、次のコマンドを実行します。

```bash
bundle exec rake callbacks:annotate
```

Rails環境を読み込み、モデルをeager loadしてから注釈を生成します。

既存の注釈がある場合は置き換え、生成結果がファイルの内容と同じなら書き込みを行いません。

### 注釈を削除する

```bash
bundle exec rake callbacks:remove
```

こちらはRailsの`:environment`タスクに依存せず、モデルファイルから注釈を削除します。

生成したコメントもコードの一部になるので、実行後は`git diff`で変更内容を確認する使い方を想定しています。

## どうやって実装したか

構成は大きく3つに分けています。

| クラス      | 役割                                     |
| ----------- | ---------------------------------------- |
| `Inspector` | モデルからコールバック情報を抽出する     |
| `Annotator` | 注釈を組み立ててファイルに追加・削除する |
| `Railtie`   | RailsにRakeタスクを登録する              |

### ソースコードではなく、実行時の登録情報を調べる

今回の実装では、Rubyのソースコードを解析して`before_save`などを探す方法は採りませんでした。

代わりに、モデルが持つ`_save_callbacks`や`_create_callbacks`などのコールバックの連鎖を参照しています。

たとえば、保存時のコールバックからフィルタを取り出す処理は、次のようになります。

```ruby
model._save_callbacks.each do |callback|
  filter = callback.filter
  # Symbolならメソッド名、Procならsource_locationを調べる
end
```

実際の実装では、ここからコールバックの種類、条件、定義元などを取り出し、表示用の情報に変換しています。

ソースコード上の記述を探すのではなく、**モデルに登録済みの情報を調べる**ことで、Concernや親クラス由来のコールバックも取得する方針です。

対象モデルは`ApplicationRecord.descendants`から取得し、抽象クラスを除外しています。現在は、ソースファイルがアプリケーションの`app/models`配下にあるモデルを対象にしています。

### コールバックの種類によって表示を変える

コールバックには、メソッド名を指定するものと、ブロックなどを渡すものがあります。

Symbolのコールバックは、メソッド名として表示します。

```ruby
before_save :normalize_name
```

ブロックやlambdaの場合は名前がないため、`Proc#source_location`で定義位置を取得して表示します。

```ruby
after_create -> { NotificationService.ping(self) }
```

この場合、注釈には`(block: app/models/user.rb:18)`のような情報が入ります。

また、Symbolのコールバックでは、`instance_method(...).owner`を使ってメソッドの定義元を調べています。

ここで表示しているのは、厳密には「コールバックを登録した場所」ではなく「呼び出されるメソッドの定義元」です。

### Rails内部のコールバックを除外する

コールバックの連鎖には、アプリケーションが明示的に登録した処理だけでなく、フレームワーク内部に登録された処理も含まれます。

すべてを表示すると読みづらくなるため、現在は次の情報を使って除外しています。

- メソッド名のパターン
- ブロックが定義されているファイルのパス
- メソッドの定義元モジュール

たとえば、`autosave_associated_records_for_`で始まるコールバックなどを除外対象にしています。

ただし、これはルールに基づく判定なので、Rails内部のコールバックを完全に識別できるわけではありません。

## ファイルを書き換えるために気をつけたこと

このGemは情報を表示するだけでなく、利用するアプリケーションのファイルを書き換えます。

そのため、注釈の内容だけでなく、追加・削除の扱いにも気をつけました。

### 注釈の範囲をマーカーで区切る

生成したコメントは、`# == Callbacks ==`と`# == End Callbacks ==`で囲んでいます。

この範囲を更新・削除の対象にすることで、通常のコメントと区別しています。

### コメントの挿入位置を考える

ファイルには、クラス定義以外にもさまざまな記述があります。

- `frozen_string_literal`などのマジックコメント
- クラスの説明コメント
- 名前空間を表す`module`

現在は、最初の`class`または`module`の位置を探し、直前に説明コメントがあればその前に注釈を入れています。

一方で、`frozen_string_literal`など、実装で判定しているマジックコメントより前には移動しないようにしています。

### 一時ファイルを使って置き換える

書き込み時は、元ファイルと同じディレクトリへ`Tempfile`を作り、書き込み後に置き換えます。

元ファイルを直接開いて書き換えるよりも、途中まで書かれた状態が残るリスクを抑えるためです。

## テストしたこと

RSpecでは、コールバックの抽出とファイルへの注釈処理を分けてテストしています。

主に確認しているのは、次のようなケースです。

- SymbolやProcのコールバックを抽出できる
- Symbolで指定された条件を表示できる
- 内部コールバックをルールに従って除外できる
- Concern由来のメソッドの定義元を表示できる
- クラスや名前空間の前に注釈を追加できる
- マジックコメントの位置を維持できる
- 注釈を追加して削除すると、元の内容に戻る
- 同じ情報で繰り返し注釈しても、内容が変わらない

特に、**追加したものを元に戻せること**と、**繰り返し実行しても不要な差分を作らないこと**を意識しました。

## 現時点での制約

小さなGemですが、まだ割り切っているところもあります。

- Procで指定した条件は注釈に表示しない
- SymbolとProc以外のコールバックフィルタは対象外
- 対象モデルの探索は`ApplicationRecord`と`app/models`を前提にしている
- ActiveRecordのコールバック内部情報に依存している

特に条件の取得には、コールバックオブジェクトの`@if`や`@unless`を参照しています。

## 初めてGemを作ってみて

普段はGemを使う側ですが、今回は小さな不便を解消する機能を、自分でGemとしてまとめてみました。

コールバックを取得する処理だけでなく、導入方法、Rakeタスク、ファイルの更新・削除、テスト、READMEまで考える必要があり、機能を作ることと、使ってもらえる形にすることの違いを感じました。

まだ改善できるところはありますが、まずは用途を絞った小さなGemとして形にできてよかったです。

ActiveRecordのコールバックを把握するのが大変だと感じている方に、使ってもらえたらうれしいです。フィードバックも歓迎します。
