本番のテーブルに`ALTER TABLE`を流すたび、毎回同じことを調べ直しています。その調べ直す内容を、MySQL 8.4を前提に1か所へまとめた備忘録です。対象はInnoDBに限り、パーティションやNDBは扱いません。

## ALGORITHMとLOCKの早見表

`ALTER TABLE`の実行方式は3種類です。MySQLは指定がなければ`INSTANT`、`INPLACE`、`COPY`の順に、実行可能な方式を選びます。

| アルゴリズム | 処理内容                                   | テーブル再構築 | 同時DML              | 所要時間   |
| ------------ | ------------------------------------------ | -------------- | -------------------- | ---------- |
| `INSTANT`    | データディクショナリのメタデータのみ更新   | なし           | 可                   | 数ミリ秒   |
| `INPLACE`    | InnoDB内部で処理。再構築の有無は操作による | 操作による     | 原則可               | 行数に比例 |
| `COPY`       | 一時テーブルへ全行コピーして入れ替え       | あり           | 不可（読み取りのみ） | 最も遅い   |

`LOCK`句は同時実行の許容度を決めます。

| 値          | 意味                                 |
| ----------- | ------------------------------------ |
| `NONE`      | 読み書きとも許可。不可能ならエラー   |
| `SHARED`    | 読み取りのみ許可                     |
| `EXCLUSIVE` | 読み書きとも遮断                     |
| `DEFAULT`   | 可能な範囲で最も緩いロックを自動選択 |

## オンラインDDLで完結する操作

実務で気にすべき境界は`INSTANT`か`INPLACE`かではなく、メンテナンス時間を確保せずに済むかどうかです。`INSTANT`と`INPLACE, LOCK=NONE`は、いずれも同時書き込みを許したまま完結します。

### INSTANTで済む操作

MySQL 8.0.29以降、カラムの追加と削除は位置を問わず`INSTANT`で実行できます。

| 操作                          | 例                                      |
| ----------------------------- | --------------------------------------- |
| カラム追加（位置指定も可）    | `ADD COLUMN memo VARCHAR(255) AFTER id` |
| カラム削除                    | `DROP COLUMN memo`                      |
| デフォルト値の変更            | `ALTER COLUMN status SET DEFAULT 0`     |
| `ENUM`や`SET`の末尾への値追加 | `MODIFY COLUMN kind ENUM('a','b','c')`  |
| 仮想生成カラムの追加と削除    | `ADD COLUMN v INT AS (a + b) VIRTUAL`   |
| インデックスタイプの変更      | `ADD INDEX idx (a) USING BTREE`         |
| テーブル名の変更              | `RENAME TO orders_old`                  |

ただし、次の場合は`INSTANT`を使えません。

- `ROW_FORMAT=COMPRESSED`のテーブル。
- `FULLTEXT`インデックスを持つテーブル。
- 一時テーブル。
- `AUTO_INCREMENT`カラムの追加。
- 同一の`ALTER TABLE`に非`INSTANT`の操作が混ざる場合。

### INPLACE, LOCK=NONEで済む操作

`INSTANT`が使えなくても、次の操作は`INPLACE, LOCK=NONE`で完結します。テーブル再構築が発生するものもありますが、その間も読み書きは可能です。

| 操作                                            | 再構築 |
| ----------------------------------------------- | ------ |
| セカンダリインデックスの追加と削除              | なし   |
| カラム名の変更（型は据え置き）                  | なし   |
| `VARCHAR`の拡張（長さバイト数が変わらない範囲） | なし   |
| 主キーの追加                                    | あり   |
| `NULL`可否の変更                                | あり   |
| `ROW_FORMAT`や圧縮設定の変更                    | あり   |

## メンテナンス時間の検討が必要な操作

次の操作は`COPY`まで落ちます。実行中は書き込みができなくなるため、実質的にメンテナンス時間の確保が必要です。

| 操作                                       | 再構築 |
| ------------------------------------------ | ------ |
| カラムの型変更                             | あり   |
| `VARCHAR`の縮小、255バイト境界をまたぐ拡張 | あり   |
| 文字セットの変換                           | あり   |
| 主キーの削除のみ                           | あり   |
| 格納生成カラムの追加                       | あり   |

`VARCHAR`は境界が分かりにくいので注意します。長さバイト数は255バイト以下で1バイト、256バイト以上で2バイトです。`utf8mb4`の`VARCHAR(63)`から`VARCHAR(64)`への拡張は境界をまたぐため、`COPY`まで落ちます。

## 気をつけること1: 明示指定で事故を防ぐ

アルゴリズムを省略すると、意図せず`COPY`に落ちても気づけません。明示しておけば、実行できない場合にその場でエラーとなります。

```sql
ALTER TABLE orders
  ADD COLUMN memo VARCHAR(255) NULL,
  ALGORITHM=INSTANT;
```

条件を満たさないときは、次のように弾かれます。

```
ERROR 1845 (0A000): ALGORITHM=INSTANT is not supported for this operation.
Try ALGORITHM=COPY/INPLACE.
```

:::message
`ALGORITHM=INSTANT`と`LOCK`句は併用できません。`LOCK=DEFAULT`のみが許可されます。


:::

## 気をつけること2: 対象テーブルのレコード数

`INSTANT`で完結する変更なら、レコード数がどれだけ多くても所要時間はほぼ変わらないですが、再構築を伴う`INPLACE`では、レコード数やインデックスの大きさに比例して実行時間が伸びます。さらに書き込み量が多いテーブルでは、オンラインDDLであっても負荷やレプリカ遅延が問題になります。実行前に、対象と同等のデータ量で所要時間を測り、許容できない場合はメンテナンス時間を確保して実行します。

## 気をつけること3: メタデータロック(MDL)

`INSTANT`であっても、開始時と終了時にはMDLが要ります。対象テーブルを参照したままの長いトランザクションがあると、DDLはそこで待たされます。さらに後続のクエリがDDLの後ろに並び、テーブル全体が実質停止します。

待ち時間の上限は`lock_wait_timeout`です。デフォルト値は31536000秒なので、セッション単位で短くしておきます。

```sql
SET SESSION lock_wait_timeout = 10;
```

待ちの相手は`sys`スキーマで特定できます。

```sql
SELECT * FROM sys.schema_table_lock_waits;
```

MDLの仕組みや、ロック待ちが発生したときの調査方法は、[MySQLのオンラインDDLでハマった話](https://zenn.dev/moneyforward/articles/7e88d7e0cd0c3d)が参考になります。

**ここからは知らなかったけど今回学んだことです。**

## 気をつけること4: 行バージョンは64回まで

`INSTANT`のカラム追加と削除は、テーブルに行バージョンを積み上げます。上限は64で、超えると次のエラーになります。

```
ERROR 4082 (HY000): Maximum row versions reached for table orders.
No more columns can be added or dropped. Please use COPY/INPLACE.
```

現在の消費数は`information_schema`で確認できます。

```sql
SELECT NAME, TOTAL_ROW_VERSIONS
FROM information_schema.INNODB_TABLES
WHERE NAME = 'shop/orders';
```

リセットにはテーブル再構築が必要です。`OPTIMIZE TABLE`か、`ALTER TABLE ... FORCE`を使います。

```sql
ALTER TABLE orders FORCE, ALGORITHM=INPLACE, LOCK=NONE;
```

リリースのたびに`INSTANT`でカラムを足す運用では、数年かけて静かに上限へ近づきます。定期的に値を見ておくと安心です。

## 気をつけること5: DML変更ログの上限

`INPLACE`の実行中に発生した更新は、いったんオンラインDDLのログ領域へ記録されます。この領域は`innodb_online_alter_log_max_size`で制限され、デフォルト値は128MBです。

```sql
SELECT @@innodb_online_alter_log_max_size;
```

書き込みの多いテーブルで長時間のDDLを流すと、途中で失敗します。

```
ERROR 1799 (HY000): Creating index 'idx_orders_user' required more than
'innodb_online_alter_log_max_size' bytes of modification log.
Please try again.
```

失敗すると最初からやり直しになるため、実行前に値を引き上げておきます。

## 気をつけること6: 容量と一時領域

再構築を伴うDDLでは、元のテーブルに加えて一時的な領域も必要です。実行前にデータディレクトリと一時ディレクトリの空き容量を確認します。特に大きなテーブルで`COPY`や再構築を伴う`INPLACE`を実行する場合は、空き容量不足による失敗に注意が必要です。

RDS for MySQLでも考え方は同じです。ホストへログインしてディスクを確認できないため、CloudWatchの`FreeStorageSpace`で空き容量を確認します。ストレージ自動拡張を有効にしていても、拡張が完了するまでの時間や設定した最大ストレージ容量があるため、DDLの実行前に十分な余裕を持たせます。

## レプリケーションへの影響

DDLはソースで完了してからbinlogに書かれます。レプリカでは同じ処理を一から実行するため、ソースでかかった時間と同程度の遅延が生じることが多いです。`INPLACE`で30分かかる変更は、レプリカでも30分前後の遅延を生みます。

`INSTANT`で済む変更では、この問題が起きません。可能な限り`INSTANT`に寄せるか、外部ツールでレプリカ側の遅延を制御します。

## 実行前チェックリスト

- 対象テーブルの行数とデータサイズ。
  - 多い場合は本番相当環境での計測。
- `ALGORITHM`と`LOCK`の明示。
- `TOTAL_ROW_VERSIONS`の残り。
- `innodb_online_alter_log_max_size`の値。
- `lock_wait_timeout`のセッション設定。
- ディスクの空き容量。
- レプリカの遅延許容量。
- 失敗時の切り戻し手順。
